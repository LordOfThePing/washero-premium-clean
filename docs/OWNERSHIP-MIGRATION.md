## 0. Decisions locked

| Decision | Choice | Consequence |
|---|---|---|
| Access to current prod | **None** — no Supabase, Vercel, MercadoPago, or Botmaker access | Clean-room rebuild from this repo. Nothing is exported or migrated. |
| Production data | **Fresh start, seed only** | New empty DB. No customers, bookings, payments, or conversation history carried over. |
| WhatsApp number | **The same Meta number Vuelto uses**, for now | One workflow published at a time (see Phase 5). No router. |
| Domain | **New domain** | DNS under our control from day one. |
| Payments | **Our own MercadoPago account** | New app, new access token, new webhook. Payments land with us. |
| Botmaker | **Dropped entirely** | `WASHERO_TRANSPORT=cloud_api`, permanently. No parallel run, no rollback transport. |

### What dropping Botmaker buys us

Most of the risk in `n8n-whatsapp-cloudapi-cutover.md` — BSP number migration, dual-transport
dedupe, parallel-run double sends, the `WASHERO_TRANSPORT` rollback flip — **does not apply**. There
is no incumbent to cut over from. We are building on the Cloud API from a blank slate.

The `BOTMAKER_*` env vars, `botmaker-outbound.ts`, `botmaker-webhook`, and `botmaker-booking-tools`
stay in the tree but are never configured or called. Only the **naming** survives: `botmaker-tools`
and the `botmaker_*` tables remain the business-logic entry point and the conversation store. Read
"botmaker" as "conversation layer", not "the vendor".

### The one accepted risk: a shared number

Vuelto and Washero share one Meta app, one WABA, one phone number. Meta registers **one webhook
callback URL per app**, so only one n8n `whatsAppTrigger` can receive at a time. We accept this by
**publishing one workflow at a time** — while Washero is active, Vuelto receives nothing, and vice
versa. That is a deliberate, reversible operational constraint, not a bug.

> **Escape hatch when this starts to hurt:** add a **second phone number to the same WABA**. It costs
> nothing, keeps the same Meta account and credentials, and makes routing deterministic — inbound
> payloads carry `entry[].changes[].value.metadata.phone_number_id`, so a single router workflow can
> dispatch on a field comparison instead of a guess. Revisit before both products are live.

#### ⚠️ Most severe finding of this migration: two atomic-booking RPC migrations were silently emptied — **and this affects `main`, not just this branch**

`create_booking_atomic`, `cancel_booking_atomic`, and `reschedule_booking_atomic` are the RPCs
**every single booking-creation path** (`create-website-booking`, `_shared/botmaker-booking-tools.ts`,
`_shared/booking-core.ts`'s `tryCreateBooking` — used by website, admin, subscriptions, Botmaker,
and the WhatsApp agent alike) calls to actually write a booking. Their defining migrations —
`20260722100000_booking_idempotency_and_atomic_insert.sql` (177 lines) and
`20260722100300_booking_cancel_reschedule_atomic.sql` (125 lines) — had been reduced to a single
`;` each. `supabase start` applied them "successfully" with zero errors, because an empty SQL file
isn't invalid SQL — it just does nothing. **The break only surfaces at runtime, on the very first
booking creation attempt**, which is exactly how it was found here: a live smoke test of
`create-website-booking` against the freshly-migrated local DB failed with
`PGRST202: Could not find the function public.create_booking_atomic`.

Traced via `git log --follow` on both files: they had their real content (verified: 177 and 125
lines respectively, matching the RPCs' current callers exactly — coverage zones, multi-vehicle
units, marketing attribution, private neighborhoods, everything) as of commit `2ccf190` ("feat: add
production-ready WhatsApp booking agent canary"), and were already reduced to `;` by the very next
commit touching them, `9943b9e` ("Migrate Washero hosting from Lovable/Cloudflare to Vercel
Nitro") — an unrelated hosting-migration commit that should never have touched these files' content
at all. **`main` has the identical bug** (checked directly: `git show main:<path> | wc -l` → `1` for
both files) — this is not specific to this feature branch.

Why production hasn't fallen over: the real hosted Supabase project's actual database already has
these functions from whenever they were first pushed, before the tracked files got corrupted —
migrations aren't replayed against a database that already has the schema, so file corruption
doesn't retroactively un-apply anything there. **The bug only bites on a fresh database rebuild from
these tracked files — precisely what this ownership migration is doing.** Without this fix, the new
project would have looked fully migrated (46/46 applied, no errors) while being unable to create a
single booking through any path, website included.

**Fix:** restored both files verbatim from `git show 2ccf190:<path>`, verified schema-compatible
(the restored `INSERT` column list already covers every column added by later migrations — coverage
zones, private neighborhoods, marketing attribution — since it long postdates all of them
chronologically), then confirmed with `supabase db reset` (clean re-apply) and a real booking
created end-to-end through `create-website-booking` (see 4.2's verification for the actual response).

- [ ] **Recommend fixing `main` too**, independent of this migration effort — any other fresh
      install from `main` today has the same silent gap.

### 4.2 MercadoPago — deferred, payment-skip mode built and runtime-verified ✅

**Completed and runtime-verified 2026-08-29.** Rather than requiring a MercadoPago account before
the booking flow can be tested at all, added `WASHERO_SKIP_PAYMENT` — a Supabase Edge Function
secret read by both `create-website-booking/index.ts` and `_shared/botmaker-booking-tools.ts`
(the two places that ever call the MercadoPago API). When set to `true`:

- Skips the MercadoPago checkout-preference call and the Transferencia bank-instructions flow
  entirely, regardless of which `payment_method` the customer actually picked.
- Marks the booking `payment_status: "paid"` at creation (via `tryCreateBooking`'s existing
  `requested_payment_status` passthrough — no core trust-boundary logic changed). `booking_status`
  is left alone, following the normal website/botmaker logic unchanged (pending/needs_review by
  coverage, or auto-confirmed for Botmaker-sourced bookings) — payment and booking-confirmation
  status are independent, and only the payment half needed forcing.
- Fires the booking-confirmation WhatsApp **immediately** instead of deferring it to wait for a
  payment webhook that will never arrive.
- Returns the normal `"booking_created"` response shape (same as the pre-existing "Pagar después"
  payment method) plus a `dev_note` field flagging that skip mode is active, so a tester can tell
  from the API response alone.

**Found and fixed a real bug while wiring this up:** `tryCreateBooking`'s returned `booking` object
never included `payment_status` at all — `create_booking_atomic`'s jsonb result doesn't echo it
back, and neither caller ever noticed because `create-website-booking` hardcoded a literal
`"pending"` string instead of reading it, and `botmaker-booking-tools.ts` read the (always
`undefined`) field and silently dropped it from every response via `JSON.stringify`. Fixed at the
source in `booking-core.ts` by echoing back the already-locally-known `payment_status` variable
(exactly what was inserted, no extra round-trip) — both callers get accurate `payment_status` now,
not just the new skip-mode path.

**Verified against the local stack** (after restoring the atomic RPCs above): a real
`create-website-booking` call with `WASHERO_SKIP_PAYMENT=true` returned
`payment_status: "paid"`, `status: "booking_created"`, no `checkout_url`, and inserted a real
`bookings` row with `payment_status='paid'`. A second call with the flag unset correctly fell
through to the real MercadoPago branch (`status: "booking_created_payment_setup_failed"`, since no
real token is configured) — confirming the flag branches both ways, not just always skipping.

- **`_shared/payment-receipts.ts` refactor** — the existing `capturePaymentReceiptFromBotmaker`

  Botmaker one. No new secrets — `WHATSAPP_CLOUD_API_TOKEN` was already on the Phase 3 secrets list.

### Two design decisions worth knowing about

1. **Dedup, and why it's not a unique constraint on `botmaker_messages`/`payment_receipts`.**
   Neither table has a unique constraint on its message-id column (confirmed — checked every
   migration). A prior migration's own comment explains why: *"we don't want to retrofit one on a
   live table with unknown existing data"* — and independently solves it with a dedicated
   `whatsapp_agent_processed_events(provider, external_message_id)` unique-indexed table. Both new
   tools reuse that exact table rather than inventing a second mechanism, with **namespaced
   provider strings** (`whatsapp_cloud_api:message` vs `whatsapp_cloud_api:receipt`) — necessary
   because a receipt-bearing image arrives as both a message *and* a receipt under the **same**
   WhatsApp message id, and each needs to claim its own idempotency key rather than colliding on
   the other's.
2. **Why `ingest_receipt` looks up a `botmaker_messages` row instead of passing the wamid straight
   through.** `payment_receipts.botmaker_message_id` is typed `uuid`, sized for Botmaker's own ids
   — a raw Cloud API message id (`wamid.HBgN...`) is not a valid UUID and the insert would fail
   with a Postgres cast error. `ingest_receipt` looks up the `botmaker_messages` row `ingest_message`
   already wrote for the same external id (n8n always ingests the message before the receipt) and
   links via that row's own uuid — falling back to `null` if not found rather than erroring.
3. **`should_bot_reply` reuses `conversation_assignments.status`**, the exact mechanism
   `request_human_handoff` and `/admin/mensajes` already use — `open`/`in_progress` ⇒ bot stays
   silent, `resolved` (or no row) ⇒ bot may reply. No new schema; an admin resolving the ticket in
   the existing UI is what resumes the bot.
